# 19 — Professional Development

Engineering is a team activity practised under constraints. This subject covers the skills that
make technical ability legible and shippable: workflows, code review, technical writing, open
source, systematic debugging, interviews, portfolio, communication, and career paths.

## What this subject covers

- Engineering workflows: branch strategies, issue tracking, definition of done, and shipping
  discipline.
- Code review: how to review (and how to be reviewed) without wasting everyone's time.
- Technical documentation: READMEs, ADRs, and runbooks written for a stranger under pressure.
- Open-source contributions: finding issues, the contribution etiquette, and landing a PR.
- Debugging methodology: the systematic process — reproduce, isolate, hypothesize, verify, fix,
  prevent.
- Technical interviews: how they are actually run, and preparation that transfers to real work.
- Portfolio development: which projects count, how to present them, and what reviewers look for.
- Teamwork and communication: status updates, disagreement, and asking for help effectively.
- Career paths: the shapes a software career takes, and how roles differ.

## Why it matters

Teams do not hire syntax; they hire people who can be trusted with ambiguity, who communicate, and
who ship. Most "failed technical interviews" are failures of articulation, and most workplace
friction is failures of review and documentation habits. This subject turns the technical
curriculum into a career — and it is placed near the end because everything you write here must be
backed by projects you actually built.

## Exercises and practice

Practice against realistic artifacts: review two provided pull requests using the checklist (one
has a subtle concurrency bug and one a security bug); write a README for an unfamiliar repository
and have someone follow it; perform one real open-source contribution (a typo fix counts — the
lesson is the process); debug a provided broken application using only the methodology; run a
timed interview set and record your think-aloud reasoning for self-review.

## Expected outcomes

You can run a complete change workflow without supervision; review code constructively with
specific, actionable comments; write documentation a stranger can follow; land an external
contribution; debug an unfamiliar system systematically; and present your capstone's decisions,
trade-offs, and failures credibly in an interview setting.

## Common blockers

- **Preparing to interview instead of preparing to engineer.** Interview performance tracks
  engineering skill more than trick memorization; the timed sets here exist to expose gaps, not to
  replace projects.
- **Portfolio of tutorials.** One project you can defend deeply beats five you followed.
- **Avoiding review.** Being reviewed early and often is the fastest skill accelerator available,
  and the least comfortable.
